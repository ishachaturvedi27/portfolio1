### Writing Classes

Classes helped us organize our Ocean Adventure game by splitting everything into different game objects like the player, sharks, coins, and NPCs. Instead of putting all the code in one place, each class handled its own job, which made everything way easier to manage.

Here are some places we used classes in our game:

- Ocean Adventure levels  
- Player (octopus) movement and controls  
- Sharks and enemy behavior  
- Coins and NPC interactions

### Basic Inheritance

Inheritance helped us avoid repeating code by letting different game objects share the same base features. For example, both players and enemies share things like position and movement.

In our Ocean Adventure game:

- enemies and players both have positions  
- sharks and NPCs both use sprites and hitboxes  
- shared movement logic comes from a base structure  

<div class="code-runner">
<pre><code class="language-javascript">
// Basic inheritance (Ocean Adventure version)

class GameObject {
    constructor(x, y) {
        this.x = x;
        this.y = y;
    }
}

class SharkEnemy extends GameObject {
    attack() {
        console.log("Shark is attacking the octopus!");
    }
}

const shark = new SharkEnemy(100, 200);
shark.attack();
</code></pre>

### Method Overriding

Method overriding was used when we wanted different game objects to act differently using the same method name. This was super useful in Ocean Adventure because not everything behaves the same way.

Examples:

- sharks damage the player  
- coins disappear when collected  
- NPCs give messages or points  

<div class="code-runner">
<pre><code class="language-javascript">
// Method overriding (Ocean Adventure style)

class SeaCreature {
    action() {
        console.log("Something is happening in the ocean...");
    }
}

class Shark extends SeaCreature {
    action() {
        console.log("Shark attacks the player!");
    }
}

enemy.action();

### Constructor Chaining

Constructor chaining helped us reuse shared properties between game objects so we didn’t have to rewrite the same code again and again. This made our Ocean Adventure code cleaner and easier to understand.

We used this idea for:

- shared movement stats for players and enemies  
- shared positions and speed settings  
- base game object setup  

<div class="code-runner">
<pre><code class="language-javascript">
// Constructor chaining (Ocean Adventure style)

class Character {
    constructor(name, speed) {
        this.name = name;
        this.speed = speed;
    }
}

class OctopusPlayer extends Character {
    constructor(name, speed, health) {
        super(name, speed);
        this.health = health;
    }
}

const diver = new OctopusPlayer("Octo Diver", 7, 100);

console.log(diver.name);
</code></pre>
</div>

### Object-Oriented Programming (In General)

Object-oriented programming is basically a way of coding where you organize everything into “objects” that represent real things in your game. In Ocean Adventure, this helped us think of everything like real parts of a system instead of just random lines of code.

We used OOP in general for:

- making the game easier to organize and understand  
- separating different parts like player, enemies, and coins  
- reusing code instead of rewriting it again and again  
- making the game easier to update and fix bugs  

In our game, everything like the octopus player, sharks, and coins were treated as objects with their own properties and behaviors. This made the code feel more structured and way less confusing. Without OOP, everything would have been in one big messy file and would’ve been really hard to manage.
